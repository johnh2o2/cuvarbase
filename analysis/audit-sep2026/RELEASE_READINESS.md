# cuvarbase 1.0 release readiness assessment and plan

Prepared 2026-09-03 against branch `v1.0-fixes` at `7d55ea2` (working tree clean). This was a read-only audit: no repository file, branch, tag or pod was touched. Evidence is cited as `file:line`, as a command with its output, or by finding number (the appendix lists all 173; 103 were adversarially re-verified, 7 were confirmed inline by the orchestrator, 63 rest on a single finder's evidence and are labelled "unverified" wherever this plan leans on them). Four open questions went to a decision panel; its recommendations and dissents are reproduced in sections 6 and 7. Many findings are duplicates from independent finders; where that is the case the duplicate numbers are listed together.

## 1. Where things stand

The 1.0 rewrite is functionally complete and has been gated once: on Jul 10 2026 the full GPU suite passed at `688da8d` (796 passed, 0 skipped, RTX A5000, `scripts/check_release_gate.py` 14/14), three audits of record exist (`analysis/tls-audit-jul2026.md`, `analysis/claims-trace-jul2026.md`, `analysis/nufft-lrt-audit-jul2026.md`), and release mechanics are staged (`analysis/RELEASE_RUNBOOK_v1.0.0.md`, `docs/RELEASE_NOTES_v1.0.0.md`, `analysis/release-staging-v1.0.0/`, a GPU-rendered docs site on the local branch `gh-pages-staging`). Since then eight commits landed on Jul 11 (`git log --oneline 688da8d..HEAD`): the README rewrite `b0fd996`, the NUFFT-LRT audit fix `a59baaa`, and the validation harness plus "Detector A" (`570b8b1`..`7d55ea2`), which changed `cuvarbase/nufft_lrt.py` by +186 lines, added 10 tests (suite now collects 806), and were never run on a device; the validation campaign the docs describe was never run either, so `docs/NUFFT_LRT_README.md` ships an empty `VALIDATION_RESULTS` placeholder and "measured" numbers with no data behind them (findings 1, 24, 45, 68, 70, 86, 103). The staged docs site predates all eight commits (finding 156), the Jul 10 gate logs are gitignored and exist only on this laptop (finding 114), and the runbook's "exactly one conflict" merge dry-run was made against a local `master` that is six commits behind `origin/master`: the real merge conflicts in `README.rst`, `cuvarbase/lombscargle.py`, `cuvarbase/pdm.py` and `cuvarbase/utils.py` (finding 113). The repository itself is not yet the "tight" tree the maintainer asked for: 42 MB of tracked non-package content (36 MB of it BLS parity `.npz` dumps), 68 files under `analysis/`, of which only about 13 are still cited by shipped code or docs while the rest are closed punchlists, agent dumps, superseded gate records and placeholder cost analyses that contradict the shipped state, nine loose markdown files in `docs/` (one still calling TLS "EXPERIMENTAL, not recommended for science use"), 47 scripts across three purposes, and 2017 root leftovers (`setup.cfg` with `universal=1`, `test_python_versions.sh` targeting Python 2.7, `publish_docs.sh`). On the code side the CPU suite is green (261 passed / 545 GPU-stubbed skips, 0 failed), flake8 hard errors are 0, packaging builds and passes `twine check`, and no correctness defect on a default path with valid input was found (the one kernel defect is on the undocumented `use_simple=True` sparse path, finding 85); the open code items are API-surface decisions that 1.0 makes expensive to change later (TLS `T0` meaning phase in one entry point and absolute time in another, a wildcard `__getattr__` that exposes `cuvarbase.np`, experimental NUFFT-LRT in the top-level `__all__`, silent all-zero periodograms on NaN input). The single biggest risk is irreversible: `README.md` is the PyPI long description and today tells users not to `pip install` and to install branch `v1.0` (75 commits behind the release branch), with eight relative links; the runbook flips it only after `twine upload`, and PyPI metadata for a version cannot be edited afterwards (findings 25, 46, 116). Verdict: the code is release quality but the branch is not tag-ready; it needs one focused content sprint on CPU (roughly two to three agent-days), one pod session to re-gate the frozen tree (about three pod-hours, plus about two if the NUFFT-LRT campaign is run), a short rehearsal, and then a purely mechanical release day once the coordinated go arrives.

## 3. Repo cleanup

Archive strategy (panel recommendation, adopted): prune in place and create one annotated tag `archive/pre-1.0-process` on the last unpruned commit, then land a single "repo prune" commit on `v1.0-fixes` before runbook step 1. Everything deleted stays reachable at `https://github.com/johnh2o2/cuvarbase/tree/archive/pre-1.0-process/<path>` and via `git show archive/pre-1.0-process:<path>`, with no duplicated content, no second tree to rot, and no stale text in GitHub search results on `master`. The only pointers are a short `analysis/README.md` index and a three-line "Historical process material" paragraph in `CONTRIBUTING.md`. Pushing the tag is a remote mutation and waits for the go like everything else; creating it locally does not. Note that this does not shrink clones (history keeps the 36 MB of `.npz`; a history rewrite is out of scope and would invalidate every SHA the audits cite).

## 7. Decisions for the maintainer

**Decision 1: cuvarbase.nufft_lrt in 1.0.0.**
Recommendation (panel): ship it QUARANTINED. Keep `cuvarbase.nufft_lrt` importable, remove `NUFFTLRTAsyncProcess`/`NUFFTLRTMemory` from `__all__` and `_LAZY_ATTRS`, move the EXPERIMENTAL warning from import to first construction, state in CHANGELOG and release notes that the module and its `run()` signature are outside the 1.x stability promise, and make `docs/NUFFT_LRT_README.md` honest (run the 1.5-hour campaign or strip every "measured" claim). Why: `from cuvarbase import *` today imports the module and emits the experimental warning for BLS/LS/PDM users who never touch it (verified under the stubs); `run(t, y, periods, ..., detector=, systematics_basis=, coeff_prior_*)` is the odd API out and its last four parameters landed after the gate; the science content was audited correct (matched filter) and the contributor is credited in the README, the release notes, the CHANGELOG and the module docstring, all of which quarantine preserves; the diff is about 40 lines and rides the mandatory re-gate. Dissent: (a) CUT Detector A only and keep the audited module (the verify-3 reviewer's preference): `git branch feature/nufft-lrt-detector-a HEAD`, then reverse-apply `604465a`'s hunks to `nufft_lrt.py` and the two test files (verified to reverse-apply cleanly at HEAD), remove the detector prose from the doc and the harness arms; the 1.0 module then matches exactly what `analysis/nufft-lrt-audit-jul2026.md` audited, and Detector A ships in 1.1 with the campaign and the contributor's sign-off.
